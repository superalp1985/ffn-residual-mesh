# 2026-09-03 Iteration 18

## 目标

在不改 llama.cpp 主推理图的前提下，做一个真实 CUDA 原型，验证三件事：

1. pinned host ring buffer 能否承载分块近似包。
2. GPU 常驻低秩残差基底能否用很轻的 kernel 合并。
3. 超级块大小和 token 窗口对 H2D、kernel、端到端延迟的影响。

## 本轮调研

本轮先核对 CUDA Runtime 和 ggml backend 的现成能力：

- CUDA 侧使用 `cudaMallocHost`、`cudaMemcpyAsync`、`cudaStreamNonBlocking`、`cudaEventRecord` 和 `cudaEventElapsedTime`。
- ggml 侧已有 `ggml_backend_tensor_copy_async`、`ggml_backend_tensor_set_async`、`ggml_backend_event_*` 和 `ggml_backend_sched_set_eval_callback`。
- 这些接口足以支持后续接入，但本轮先保持独立原型，避免把实验误差和 llama.cpp 调度耦合。

参考入口：

- `vendor/llama.cpp/ggml/include/ggml-backend.h`
- `vendor/llama.cpp/examples/eval-callback/README.md`
- NVIDIA CUDA Runtime API 中 memory copy、host allocation、event timing 章节。

## 原型定义

固定维度：`hidden=2048`、`top_k=4`、残差基底 `rank=64`。

近似包布局：

```text
base[window, 2048]       fp16
coeff[window, 4]         fp16
indices[window, 4]       uint16
```

因此理论包大小为 `4112 B/token`。GPU 常驻 `U[64, 2048]`，kernel 计算：

```text
y_hat[t,h] = base[t,h] + sum_i coeff[t,i] * U[indices[t,i],h]
```

三个模式：

- `base_only`：只搬运基础输出。
- `base_plus_residual`：搬运基础输出、系数和索引，然后合并。
- `exact_fallback_evicted`：保守地每个 token 重传一次完整 down 权重代理（10,321,920 B），再执行 checksum kernel。该模式是回退搬运压力代理，不是完整精确 FFN。

测试超级块：64 KiB、256 KiB、1 MiB；测试窗口：1、16、64 token；每组 warmup 10 次、计时 100 次。

## 结论

1. 原型链路成立：pinned ring buffer、异步 H2D、GPU 常驻低秩基底和轻量合并 kernel 均可运行。
2. 在 64-token 窗口中，近似包实际搬运量为 5,120 B/token（64 KiB 块），而保守回退压力代理约 10 MiB/token；数量级差异明确。
3. 近似 kernel 只有约 0.03–0.05 ms/窗口，当前原型仍以 H2D 和块对齐为主；这符合“用算力换显存/带宽”的方向。
4. 1 MiB 超级块对短窗口浪费明显；64 KiB 对 decode 风格窗口更合适，1 MiB 更适合长 prefill。
5. 不能把本轮结果称为端到端加速。尚未接入 llama.cpp，也没有测 CPU 预展开、真实 PCIe 并发、GPU gather 与图调度重叠。
