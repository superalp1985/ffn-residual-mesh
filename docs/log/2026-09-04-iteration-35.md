# 2026-09-04 Iteration 35: Continue Decision

## Decision

Continue the project, but stop enumerating unstructured formula variants. The next phase is an engineering prototype of:

```text
cold start: exact Q4 high/low split + compiled radix partial-sum tables
runtime:    bounded table reads for the main term + exact packed 2-bit residual on GPU
pipeline:   1024-row residual tiles with pinned double buffering
```

The decision is based on actual layer-23 data, not static compression claims.

## Evidence

### Exactness

- The base-4 table reconstructs the signed-int8 high-code dot product exactly.
- The full high/low merge has maximum absolute error below `5e-7` in float32 output replay.
- A 32-token holdout check for both gate and up projections produced `max_integer_error = 0` for every token.
- The complete low-code residual is lossless; its 2-bit packing is transport encoding only.

Artifacts:

- `results/exact_radix_pipeline_l23_20260904.json`
- `results/exact_radix_table_holdout_l23_20260904.json`

### Main-term access trade-off

Native single-thread lookup on the i7-14650HX:

| block size | table per projection | runtime table read | lookup time per projection |
|---:|---:|---:|---:|
| 2 | 96 MiB | 24 MiB/token | 2.07--2.43 ms |
| 4 | 768 MiB | 12 MiB/token | 0.95--1.25 ms |

The table is large but feasible in host RAM. Runtime does not scan the high-code stream; it performs four bounded state lookups per input block. Block size 2 is a viable low-RAM fallback, while block size 4 is the likely decode choice if RAM is available.

### Activation state error

The table is exact for the represented int8 activation state. Quantizing the original layer-23 activation to groupwise int8 introduces a separate FFN error:

- group 4: holdout relative L2 about `0.162%`;
- group 8: about `0.223%`;
- group 16: about `0.304%`;
- group 32: about `0.387%`;
- group 64: about `0.508%`.

This is `H*epsilon_x`, not weight residual error. Group 4/8 are the first candidates for a stricter accuracy budget.

Artifact: `results/exact_radix_activation_error_l23_20260904.json`.

### GPU residual pipeline

The Triton residual kernel reproduced the CPU residual to about `1e-7` relative L2. With actual layer-23 gate/up residual payloads:

- 256-row tiles: launch overhead dominates;
- 1024-row tiles: double buffering reduced copy+compute time by about `24%` versus serial execution;
- 6144-row whole-layer tiles: overlap was effectively zero.

Artifact: `results/gpu_residual_tile_sweep_l23_20260904.json`.

## Comparison with existing baseline

The existing llama-bench reference on this RTX 4070 Laptop GPU measured about `131 tok/s` with all layers on GPU and about `43 tok/s` with CPU-only placement. The current radix/table code is not an end-to-end replacement yet; it is a layer-level proof. Its gate+up main lookup is about `2.4 ms` in native single-thread code, and the residual pipeline is about `1.25 ms` with 1024-row tiles. Down projection, graph integration, and synchronization are still unmeasured.

Therefore the result is a **continue-with-scope** decision, not a claim of model-level speedup.

## Stop/continue boundary

Continue if the next integrated prototype demonstrates at least one of:

1. residual copy wait is hidden by the main/down compute;
2. layer latency is below the corresponding CPU-offloaded FFN latency;
3. the same schedule scales to a larger-than-VRAM model without reintroducing dense main-weight scans.

Stop this formula branch if native table lookup plus merge remains slower than the offloaded baseline after C++/CUDA integration, or if groupwise activation state error exceeds the model error budget and exact epsilon correction requires a dense main scan.

## Next iteration

1. Implement a C++/CUDA layer runner with a 1024-row residual ring buffer.
2. Keep gate/up merge before the original SiLU and down projection.
3. Measure GPU wait, overlap, layer latency, and peak VRAM together.
4. Test groupwise activation state sizes 4 and 8 before considering any lossy residual mode.
