# Iteration 77: Explain the 1.1 ms Resident FFN Span

Date: 2026-09-11

## Question

The measured resident Qwen3.8-27B FFN layer is around `1.1 ms`. Determine
whether this is a missing-DMA/synchronization problem or the expected cost of
the current batch-1 quantized dependency chain.

## Evidence

Layer 25, Q5_K gate/up and Q5_K down:

```text
gate/up + SwiGLU: 0.716 ms median after long warmup
down projection:  0.402 ms median
sum of medians:    1.118 ms
host wall median:  1.326 ms
```

This is `artifacts/l25_long_300.json`, with 300 warmup invocations and 300
samples, `block_rows=4`, `num_warps=2`, `base_block_groups=16`, and
down `rows=2`, `warps=2`, `qblocks=4`. The existing script's
`critical_gpu_ms` field sums the gate/up and down stage medians. It omits
the group-sum reduction and inter-stage submission intervals, and is NOT a
directly measured complete-FFN median. The full two-layer CUDA Graph in
iteration 75 remains the cleaner contiguous device-chain measurement.

The best previously measured gate/up launch shape was approximately
`0.70 ms`; changing the shape to more warps or larger group tiles made it
slower. The long-run sample also reached approximately `0.686 ms` for
gate/up and `0.396 ms` for down, so the implementation is not uniformly stuck
at a multi-millisecond synchronization stall.

The measured path has this real dependency:

```text
gate/up residual + base -> SwiGLU -> quantized down
```

The current down kernel consumes the completed SwiGLU vector. Its execution
therefore follows gate/up in the existing implementation. A different tiled
algorithm could accumulate partial down contributions earlier, but adding
streams alone does not implement that algorithm or remove its dependencies.

The layer-25 runtime weight footprint is `217,251,840 B`, or `217.25 MB`
decimal / `207.1875 MiB`, excluding verification-only artifact data:

| Runtime operand | Bytes |
|---|---:|
| Gate/up packed residual codes | 111,411,200 |
| Gate/up FP32 alpha | 22,282,240 |
| Gate/up FP32 base coefficients | 22,282,240 |
| Original packed Q5 down | 61,276,160 |
| Total | 217,251,840 |

The original three Q5_K projections total `183,828,480 B`. This particular
exact split representation is **18.18% larger**, not a compressed residual
representation. Moving coefficients to CPU saves 22,282,240 device bytes but
also introduces input-dependent CPU work and result transfers.

Using the reported 128-bit memory bus and 8,001 MHz memory clock gives an
idealized peak of about `256 GB/s`; the footprint divided by the measured
stage sum of `1.118 ms` is about `194 GB/s`.

```text
Assumed one external-memory read per runtime weight byte:
217,251,840 / 256,032,000,000 = 0.849 ms
```

This is a conditional traffic model, NOT a measured DRAM throughput or a
strict hardware latency lower bound. L2 reuse, repeated loads, decoding,
reductions, memory transaction efficiency and omitted timing intervals are
not accounted for. PyTorch reports a 32 MiB L2 cache on this device.

The `0.849 ms` estimate is useful for rejecting an arithmetic-only timing
estimate; it does not prove that the current kernel saturates memory bandwidth.

## Additional checks

### Controlled native-versus-split comparison

The first version of this diagnostic had a benchmark-harness defect: several
temporary native-path output buffers were not retained after CUDA Graph capture.
CUDA Graph replay uses fixed device addresses, so those allocations could be
reused and corrupt the native reference. The harness now keeps all captured
intermediates alive and compares both GPU paths against an independent GGUF
`dequantize` FP64 reference.

Verified run:

```text
artifacts/l25_native_vs_split_paired_verified.json
layer=25, warmup=3 s, repeats=51, inner=8
```

| Variant | Uninstrumented median | P95 | Max reference relative L2 |
|---|---:|---:|---:|
| Native packed Q5 | 1.315 ms | 1.382 ms | 2.26e-7 |
| Exact split, r4/w2/g16 | 1.302 ms | 1.375 ms | 2.44e-7 |
| Exact split, r8/w4/g8 | 1.541 ms | 1.606 ms | 2.55e-7 |

The r4/w2/g16 result is statistically close to native in this run; an
earlier shorter run measured it about 6% slower. Treat that difference as
run-to-run variability, not a proven speedup. The separate instrumented stage
pass reports:

| Variant | Gate/up + SwiGLU | Down | Device span |
|---|---:|---:|---:|
| Native | 0.642 ms | 0.397 ms | 1.051 ms |
| Split r4/w2/g16 | 0.663 ms | 0.399 ms | 1.071 ms |

CUDA event nodes perturb timing, so this table is diagnostic only. It
indicates the split overhead is concentrated in gate/up decoding and base
coefficient accumulation; the down projection is effectively unchanged.

The test fixture verifies mixed Q5/Q4 artifacts and checks the full FFN
against an independent dequantized reference. The complete test suite passes
with `109 tests`, `3 skipped`.

- `artifacts/l25_br4w2_d2w2q4.json`: 20 warmup / 15 samples,
  stage-median sum `1.260 ms`, wall median `1.490 ms`.
- `artifacts/l25_clock_sync.json`: 500 warmup / 500 samples with a separate
  live `nvidia-smi` monitor, stage-median sum `1.317 ms`, wall `2.197 ms`.
  These slower figures show measurement/system variability; they are not
  evidence of a kernel regression or a proven frequency cause.
- P5 / low clocks were initially observed after a benchmark completed.
  That is an idle observation and does NOT identify the benchmark's operating
  clock. The subsequent console monitor had no saved per-kernel correlation,
  so the low-clock hypothesis remains unproven.
- `artifacts/l25_cpu_base_51.json`: CPU-base mode, 3 seconds requested warmup,
  51 samples, 8 CPU threads, grouped residual rows=8/warps=4/groups=16.
  CPU base median `3.855 ms`, wall median `8.224 ms`, output relative L2
  `2.44e-7`. This was not a randomized same-process comparison, and starts
  with a host activation; it is insufficient to prescribe a CPU/GPU placement
  universally, but provides no reason to switch this layer to CPU base.

## Finding

`1.1 ms` alone is not evidence that the GPU is waiting for host DMA.
The resident chain removes per-invocation weight H2D, but not device-memory
reads. The measured stage intervals and traffic model point toward the
quantized GEMV/decode path as the next target. Attribution between DRAM,
instruction throughput, scheduling and register pressure still needs a
controlled comparison or hardware counters.

No faster kernel or new default was delivered in this iteration. The next
bounded comparison should use identical inputs and operating conditions:

1. Original packed Q5 FFN versus the exact resident split.
2. Fixed-buffer CUDA Graph timing with paired/randomized sample order.
3. Runtime weight-byte ledger plus load-time clock samples recorded with the
   measurements, not a post-run idle snapshot.
4. Tune the slower decoding stage or reduce auxiliary storage only after
   identifying a repeatable difference. The current evidence points first to
   the mixed-Q5 grouped decoder and coefficient-load path, not to missing host
   DMA.

This retains the project's resource-exchange objective, but does not assume
that naming data "residual" makes its encoded size smaller.

not establish full-model generation throughput, SM occupancy, or a 20
