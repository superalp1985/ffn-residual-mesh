# 2026-09-03 Iteration 23

## 目标

测量 CPU 生成真实 `base + top-k coeff + indices` 连续 packet 在不同 batch 下的摊销，判断把 FFN 基础项放入 RAM/CPU 后是否会形成新的串行瓶颈。

## 先行调研

- pinned/non-blocking 只优化 CPU/GPU 传输，不能消除 CPU 矩阵乘本身。
- batch=1 才代表单路自回归 decode；batch 4/16/64 只能代表 prefill 或多个独立序列，不能用来夸大单用户 decode 速度。
- 现有脚本的 `load_tensor` 被顶层 `scikit-learn` 导入阻塞，本轮将聚类依赖改为 `fit()` 内按需导入，不改变聚类实验行为。

## 实现

新增 `scripts/profile_cpu_ffn_batches.py`，按 batch 测：

1. 精确 CPU FFN。
2. Chebyshev degree-5 基础项。
3. input-rank=128、output-rank=64 的残差系数。
4. 基础输出 fp16 + top-k=4 系数/索引的连续 `4,112 B/token` packet。

环境：`E:\MiniMaxH3\ComfyUI\venv`，Python 3.12.10，NumPy 2.5.1，24 logical CPUs。

## 结果

| batch | 场景 | exact FFN us/token | full packet us/token | 24 层串行代理 | 24 层代理 tok/s |
|---:|---|---:|---:|---:|---:|
| 1 | 单路 decode | 2,468 | 2,716 | 65.18 ms/token | 15.34 |
| 4 | prefill/并发序列 | 2,115 | 2,099 | 50.37 ms/token | 19.85 |
| 16 | prefill/并发序列 | 520 | 791 | 18.99 ms/token | 52.67 |
| 64 | prefill/并发序列 | 276 | 541 | 13.00 ms/token | 76.95 |

残差系数计算在 batch=1 仅约 `11.1 us/token`；主要成本仍是 gate/up/down 三次矩阵投影。packet 打包本身只有几十微秒量级，独立计时抖动会导致少量负差值，不应过度解释。

## 结论

1. 单路 decode 的 CPU 路径按 24 层粗略外推仍有约 `15 token/s`，证明“用 CPU 算力换显存/PCIe”不是离谱方向。
2. prefill 或并发序列可以明显摊销矩阵乘，但不能用于单路 decode 承诺。
3. 当前 Chebyshev 基础项仍完整读取 gate/up/down 权重，batch=1 比精确 CPU FFN慢约 `10%`；仅替换 SiLU 没有减少权重扫描。
4. 下一轮必须真正做离线展开：把常数/线性项合成矩阵，只保留少量高阶 CP 通道，目标同时降低 RAM 权重读取和 CPU MAC。
