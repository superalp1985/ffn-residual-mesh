# 2026-09-03 Iteration 33: Exact Residual Default

## Decision

Residual compression is not required for the mathematical baseline. The default residual is lossless: retain every low-digit/code residual and only bit-pack it. Bit-packing changes transport width but does not discard information. Any clipped 1/2/3-bit residual mode is a separate lossy experiment and must not be used to judge whether the split-and-merge identity is correct. If the residual is instead stored as ordinary 8-bit/16-bit values, it remains exact but loses the transport benefit; that is a bandwidth choice, not an accuracy choice.

For a code split such as:

```text
q = 4*q_hi + q_lo
```

`q_lo` is an exact 2-bit residual. The merge is:

```text
dot(x, q) = 4*dot(x, q_hi) + dot(x, q_lo)
```

No residual approximation is present unless `q_lo` is itself clipped, omitted, or quantized again.

## Runtime boundary

```text
cold start:
    scan raw Q4_K once
    compile main-term formulas / partial sums / finite-state tables
    materialize exact packed residual tiles

runtime:
    evaluate only the compiled main-term artifact
    transfer exact packed residual tiles to GPU
    compute residual dot products
    merge before the original SwiGLU
    never scan raw weights or a dense expanded main-term stream
```

The remaining research question is therefore not whether an uncompressed residual can be correct; it can. The question is whether the cold-start compiler can turn the bulky main term into bounded-access tables/formulas. The new ledger script records this separately from residual correctness.

## Next experiment

`scripts/estimate_exact_state_table_ledger.py` enumerates input block sizes and state widths. It reports table RAM, runtime table bytes per token, and exact packed residual payload. A state-table candidate is rejected if it approaches dense main-term reads or has an impractical table footprint, even when its arithmetic identity is exact.
