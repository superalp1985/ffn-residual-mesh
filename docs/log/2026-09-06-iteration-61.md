# Iteration 61: GPU-resident activation chaining

日期：2026-09-06

## 本轮调研

在改动前核对了 PyTorch CUDA stream/event 与 CUDA Graph 语义。官方接口把
`wait_event` 定义为“让 stream 后续工作等待 event”，CUDA Graph 的收益主要是
固定工作链的重复提交开销，而不是减少算术量。因此本轮把优化边界放在：

```text
上一层 GPU 输出 -> 下一层直接消费
```

不再把 activation 复制到 runner 私有缓冲，也不再为已经在 GPU 上的 activation
额外制造 host staging。

## 实现

`TiledResidentGateUp.run_device()` 现在：

- 只接受 runner 同设备上的 contiguous CUDA `float32` activation；
- 直接对调用者 tensor 计算 `group_sums`；
- group reduction、fused residual/base/SwiGLU 和可选 down 在同一消费 stream
  排队；
- `activation_h2d_bytes == 0`、`activation_d2d_bytes == 0`；
- 增加 `synchronize=False` 异步提交模式，适合连续排多层后只同步一次；
- 异步模式禁止立即读取 numpy 输出，返回 `completion_event` 作为边界。

此前独立 `base_stream` 用于隐藏 host-to-device base 上传；设备 activation 路径
已经没有 H2D，所以跨 stream event 只增加依赖，不带来可隐藏的复制工作，已移除。

## Qwen3.8-27B 实测

硬件：RTX 4070 Laptop，8 GiB，CUDA 13.0，PyTorch 2.9.1+cu130。

真实 layer 3 与 layer 21 artifact 的单层整层 resident gate/up + IQ4_NL down：

| layer | ordinary wall median | CUDA Graph wall median |
|---:|---:|---:|
| 3 | 约 3.16 ms | 约 2.47 ms（此前样本） |
| 21 | 约 2.53 ms | 约 2.38 ms（此前样本） |

两层 GPU activation 链（layer 3 -> layer 21）：

```text
同步逐层调用 wall median：约 19.29 ms
异步同 stream GPU span median：约 17.63 ms
CPU enqueue median：约 2.77 ms
每层 activation H2D：0 B
每层 activation D2D：0 B
每层 base H2D：0 B
```

该链路只证明设备侧排队和流边界可工作，不代表 27B 端到端生成速度。当前
测试还没有包含 attention、KV cache、非 resident 层换入和真实 token 激活分布。

## 下一步

1. 把异步 device-chain 接入多层 runner，避免每层 Python 调用创建大量 timing
   event；
2. 将 down projection 的 workspace 和输出复用纳入链路，减少 allocator 抖动；
3. 用 Nsight Systems 或允许 GPU performance counters 后再测 SM active、kernel
   gap 和 copy/compute overlap；
4. 只有在多层链的 GPU span、CPU enqueue 和显存峰值都稳定后，才评估完整模型
   的速度上限。
