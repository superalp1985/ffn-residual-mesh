# 2026-09-04 Iteration 43: CPU Table Production Boundary

## Research first

Rechecked the existing C++ CPU evaluator results before changing the Python bridge. The C++ runner already measures the radix table lookup path with a resident thread pool; this round uses Python only as a correctness oracle to avoid confusing interpreter/NumPy scheduling overhead with the intended C++ implementation.

## Experiment

Enabled `--base-mode table --cpu-threads 8` in `scripts/benchmark_cpu_base_gpu_full_ffn.py`. Each 2048-row tile is generated from the persisted block-2 radix partial-sum table, then sent with the same residual packet to the GPU full chain.

Results for layer 23, three repeats:

- CPU table production wall time: about `300 ms`;
- GPU copy-active time: about `0.85 ms`;
- GPU compute-active time: about `0.31--0.37 ms`;
- critical path: about `300 ms`;
- full output relative L2: `1.18e-4`.

## Interpretation

The formula and artifact are correct, but Python per-tile loops are not a runtime implementation. They create hundreds of small NumPy operations and interpreter scheduling overhead, completely hiding the GPU work. This does not invalidate the architecture: previous C++ measurements put the same CPU table evaluator in the millisecond range and showed stable CPU/GPU overlap.

## Decision

Keep Python table mode as a correctness oracle only. Do not use its `300 ms` timing in the bandwidth/compute tradeoff. The next implementation step is a C++ full runner that reuses the existing threaded radix evaluator, copies only the small base tile plus exact residual packet, and feeds the same GPU `SwiGLU + down` partial kernel.
