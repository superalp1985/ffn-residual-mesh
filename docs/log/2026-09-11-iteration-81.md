# Iteration 81: FP16 Resident Base Coefficients

Date: 2026-09-11

## Objective

Test whether the static affine-base coefficient matrix can remain resident on
the GPU in FP16 while the fused residual/base kernel widens coefficients to
FP32 for multiplication and accumulation. The goal is to reduce valuable VRAM
reads and residency without changing the exact residual encoding.

## Research basis

- NVIDIA CUDA floating-point guidance documents IEEE-754 formats, rounding,
  FMA behavior, and the need to measure GPU numerical differences separately:
  https://docs.nvidia.com/cuda/floating-point/index.html
- Triton's cast API documents FP downcast rounding modes (`rtne` and `rtz`):
  https://triton-lang.org/main/python-api/generated/triton.language.cast.html

Both pages were retrieved on 2026-09-11. The web tool returned empty results,
so the official pages were retrieved directly with HTTP (status 200).
This implementation converts the coefficient array with NumPy at cold start,
uploads that FP16 tensor, and uses the existing Triton
`tl.load(...).to(tl.float32)` widening path. The cast documentation is background,
not a claim that this implementation invokes Triton's downcast operation.

## Arithmetic

For row `r`, 32-element group `g`, and dynamic activation `x`:

```text
S[g] = sum_j x[g,j]
y[r] = sum_g (alpha[r,g] * sum_j residual[r,g,j] * x[g,j] + C[r,g] * S[g])
C16[r,g] = round_fp16(C[r,g])
delta_y[r] = sum_g (C16[r,g] - C[r,g]) * S[g]
```

The final line describes the additional storage-rounding error before SwiGLU,
apart from floating-point evaluation order. FP32 accumulation cannot recover
the discarded coefficient bits. After SwiGLU and down, the error depends on
the input and both projections. No full-model quality bound is established.

## Implementation

`TiledResidentGateUp` now accepts `base_dtype="float32"` (default) or
`base_dtype="float16"`/`"fp16"`. FP16 is opt-in and guarded because it is an
approximation:

- only the full-layer resident GPU-base path is accepted;
- non-finite and out-of-range coefficients are rejected before device storage;
- residual codes and alpha tensors remain unchanged;
- run results report actual coefficient residency bytes; diagnostic configs
  also record storage dtype;
- the latency diagnostic exposes `--compare-fp16-base` and labels the variant
  `approximate_fp16_base_affine_split`;
- the existing strict `1e-4` reference threshold is not relaxed. A report containing an
  FP16 candidate therefore correctly reports `validation_passed=false` when
  that candidate exceeds the threshold. This is a numerical acceptance
  criterion, not a proof of mathematical exactness.

## Results: Qwen 3.8 27B Layer 25

Artifact: `data/resident_qwen38_layer25_exact_v2` (Q5 gate/Q5 up, Q5 down)

Protocol: 5 s warmup, 101 randomized paired rounds, 16 graph replays per
round, fixed CUDA graph addresses. Seed 8101 used two independent validation
inputs; seed 8102 used four. The timed input in each run was a fixed random
vector, not an activation captured from end-to-end inference.

| Variant | Median FFN graph | P95 | Base resident | Total runtime weights | Max ref relative L2 |
|---|---:|---:|---:|---:|---:|
| Native packed Q5 | 1.131 ms (seed 8101) / 1.153 ms (8102) | 1.180 / 1.319 ms | n/a | 183,828,480 B | 2.37e-7 / 2.31e-7 |
| Exact FP32 split | 1.164 / 1.173 ms | 1.213 / 1.329 ms | 22,282,240 B | 217,251,840 B | 2.53e-7 / 2.55e-7 |
| FP16-base split | 1.113 / 1.127 ms | 1.161 / 1.247 ms | 11,141,120 B | 206,110,720 B | 1.04e-4 / 1.06e-4 |

The FP16 base reduced the static coefficient footprint by exactly 50% and
reduced total split runtime storage by 11,141,120 B (about 5.1% of the split
payload). The coefficient footprint is 21.25 MiB versus 10.625 MiB.
The ratio of variant medians improved by 4.35% and 3.88% versus the FP32 split
path in these two runs. The candidate won 94/101 and 93/101 paired rounds,
respectively. It exceeded the strict numerical threshold by approximately
3.5% and 6.3%, so it is not an exact replacement and is not enabled by default.

## Finding

This is a useful memory/latency tradeoff for an explicitly approximate mode,
not proof that the split algorithm is exact at FP16. The exact FP32 path remains
the default. Both FP16-base payloads remain larger than the original packed
weights by 22,282,240 B. This is not a compression victory over original Q4/Q5.
H2D is already zero inside the timed graphs for every variant, so this does
not measure an additional PCIe saving. Lower storage bytes also do not
establish the exact number of physical DRAM bytes read.

Attention, KV cache, offloaded layers, input transfer, host orchestration and
token sampling are excluded. These single-layer runs do not establish
27B end-to-end 20 tokens/s or the 0.3-0.5 ms FFN target.

Possible follow-ups are selective higher-precision coefficients or a more
compact exact coefficient/scale layout. A second FP16 correction matrix would
bring coefficient storage back to four bytes per entry before metadata; any
such candidate must first pass a complete byte-budget and instruction-cost
check. Do not promote a candidate on isolated kernel timing alone.

## Verification

The original provisional FP16 pointwise SwiGLU comparison failed (4/256
elements at `rtol=atol=4e-3`). Replacing it with a vector relative-L2 metric
does not eliminate that failure or establish pointwise equivalence. Separate
tests now compare GPU output to independent GGUF FP64 weights plus the
explicit coefficient-rounding correction above, including Q4/Q4, Q5/Q5 and
Q5/Q4, multiple activations, CUDA graph replay and device-input execution.
The real-layer diagnostic retains the strict numerical threshold unchanged.

Validation also rejects unsupported multitile FP16, invalid dtypes,
non-finite coefficients and FP16 overflow. A non-finite error following a
finite error fails aggregate validation rather than being hidden by `max()`.
