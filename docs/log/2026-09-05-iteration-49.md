# Iteration 49: CPU lookup evaluator, SIMD, and software prefetch

Date: 2026-09-05

## Scope and research before changes

The user requested publishing the complete-FFN worker results and investigating
why local base lookup plus residual merge is slower than direct CPU execution.
Commit `14f2a16` already contains the worker results on `origin/main`.

Primary references consulted before this iteration:

- Microsoft T-MAC, https://github.com/microsoft/T-MAC :
  bit-sliced low-bit execution, small activation-derived LUTs and CPU shuffle
  instructions. This is NOT the same as our large cold-expanded weight table.
  Its published speedups do not establish speedups for our Q4_K split.
- GCC built-in prefetch documentation,
  https://gcc.gnu.org/onlinedocs/gcc/Other-Builtins.html :
  software prefetch is a hint for known future addresses, not a guarantee that
  memory latency disappears. Address construction must remain in bounds.

The web search tool returned empty results; primary pages were retrieved
directly over HTTPS instead. No third-party performance numbers are imported
as local evidence.

## Evidence and hypotheses

Local CPU: i7-14650HX, 16 cores / 24 logical processors, reported 30 MiB L3.

- Block-4 cold table: 768 MiB per gate/up projection.
- Selected table values: 12 MiB per token/projection, before metadata.
- Source Q4_K projection: approximately 6.75 MiB (verify from actual loader).
- Existing C++ evaluator stores a groups-by-rows int32 accumulator and revisits
  it for each digit and block; Python additionally allocates selected arrays.
- `-O3 -march=native` can auto-vectorize the old C++ loop. Do not describe it
  as necessarily scalar without inspecting compiler output.
- Existing `median_like_ms` is an arithmetic mean, not a median.
- Existing CUDA runner produces both full CPU bases before launching the GPU.
  Its `max(cpu,gpu)` result is a lower-bound estimate, not measured CPU/GPU overlap.

### Measured result (Qwen3.5-2B layer 23, Windows, i7-14650HX)

The new benchmark uses the same packed codes and alpha/beta metadata for direct
and table paths. It includes state preparation, persistent worker dispatch,
projection, and metadata merge; it excludes file I/O and cold table creation.
The direct path is a cold-repacked Q4 nibble baseline, not llama.cpp's fully
optimized Q4_K kernel.

Block-4, one token, one worker:

| path | gate median |
|---|---:|
| direct packed-Q4 AVX2 | 0.765 ms |
| old table loop | 2.257 ms |
| fused table, no prefetch | 1.739 ms |
| fused table, prefetch distance 4 | 1.273 ms |

Block-4, one token, eight workers:

| path | gate median |
|---|---:|
| direct packed-Q4 AVX2 | 0.203 ms |
| fused table, prefetch distance 2 | 0.265 ms |
| fused table, prefetch distance 8 | 0.233 ms |

The corresponding up projection is similar. Block-2 is worse: one worker
fused/prefetch-4 is about 4.38 ms versus direct 0.763 ms; eight workers are
about 0.67 ms versus direct 0.30 ms. Block-2's larger number of table entries
and address lookups dominates.

Exactness checks: integer mismatches `0`; maximum split-merge FP32 error
`1.43e-6` in the small native test. The Qwen benchmark also reports zero
integer mismatches and exact high/low recombination within the configured
float tolerance.

Conclusion: software prefetch plus fused AVX2 removes a substantial part of the
old implementation overhead, but table lookup is not automatically faster than
direct contiguous Q4. For this layer, block-4 is the only viable table setting
and remains slightly slower than the direct CPU reference at eight threads.
The dominant residual issue is table working-set locality and address entropy,
not a missing conservation identity.

Mathematical equivalence does not imply equal elapsed time. More memory
traffic, poor locality, dependencies and synchronization can dominate saved
arithmetic without violating any conservation principle.

## Bounded plan

1. Add native correctness tests for signed-int8 extremes, multiple inputs,
   block sizes 2/4, row tails, and high/low reconstruction.
2. Add an AVX2 evaluator with exact int16 group accumulation, fused metadata
   merge, and optional prefetch of selected future table entries.
3. Compare old evaluator, new evaluator, prefetch distances, and direct packed
   Q4 SIMD under the same inputs and thread budget.
4. Measure input-varying and repeated-input workloads separately; include
   input preparation and full output verification.
5. Integrate only correctness-verified CPU kernels into the existing CUDA
   bridge and report measured totals separately from overlap estimates.
6. Run tests, preserve raw results, update documentation, commit and push.

Do not promise zero bubbles, lower FLOPs, or an end-to-end speedup before
measurement. CPU cache misses and GPU occupancy require hardware profiling;
elapsed time and logical byte counts alone cannot establish them.
