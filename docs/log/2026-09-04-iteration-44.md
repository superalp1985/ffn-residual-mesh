# 2026-09-04 Iteration 44: 27B-class FFN Budget and C++ Full Chain

## Research-first decision

This round keeps the existing scope: no claim of end-to-end 27B acceleration. The purpose is to quantify whether the measured layer-23 bridge can support a larger dense FFN when the main term is pre-expanded in host RAM and only the exact low-bit residual enters GPU memory.

The budget is parameterized because “27B” does not identify one architecture. Two sizing points are recorded:

- `hidden=5120, ffn=13824, layers=48`;
- `hidden=6144, ffn=16384, layers=40`.

Both use the current exact residual layout: 2-bit packed code plus one fp32 alpha per 32 input values, Q4_K source cost approximated as 4.5 bits/weight, 2048-row tiles and two GPU slots.

## C++/CUDA full-chain runner

Added:

- `src/exact_cpu_base_gpu_full_ffn_runner.cu`
- `scripts/export_down_fp16.py`
- `scripts/build_and_run_full_ffn_cuda.py`

The runner reuses the resident radix table evaluator for CPU base outputs and executes GPU `residual -> base+residual -> SwiGLU -> resident fp16 down` with copy/compute double buffering. The down tensor is exported only as a cold-start/reference artifact for this prototype.

Layer 23, block 2, tile 2048, eight CPU threads, RTX 4070 Laptop GPU:

- CPU gate+up base production: about `1.96 ms`;
- GPU serial copy+full-chain: about `1.33 ms`;
- GPU double-buffer full-chain: about `1.07 ms`;
- GPU-only overlap improvement: about `1.25x`;
- pre-expanded CPU/GPU critical lower bound: about `1.96 ms`, versus `3.27 ms` serialized, about `1.67x`;
- 1024-row tiles raised GPU overlap to about `1.44 ms`, so 2048 remains the current candidate.
- The `block=4` table comparison at the same tile/threads gave CPU base about `2.38 ms`, GPU serial about `1.44 ms` and GPU overlap about `1.01 ms`; its GPU-only overlap gain was better, but the larger table did not reduce the CPU critical term versus `block=2` in this run.

The local device reports `8188 MiB` total framebuffer memory and a maximum PCIe link of Gen4 x8. At idle the driver reported Gen2 x8; the measured pinned H2D path in the experiment was about `12.07 GB/s`, so the budget uses a conservative effective `12 GB/s` rather than the theoretical link rate.

The C++ runner reports scheduling and kernel completion. The Python bridge remains the numerical oracle against the original GGUF Q4 path: full down relative L2 is about `1.18e-4`, and per-tile SwiGLU relative L2 is about `1e-7`.

## 27B-class budget

For `hidden=5120, ffn=13824`:

- gate/up exact residual plus alpha: `50.625 MiB/token/layer`;
- CPU base gate/up vectors: `108 KiB/token/layer`;
- one resident fp16 down matrix: `135 MiB/layer`;
- two-slot full-chain workspace: about `15.2 MiB`;
- with a 1 GiB runtime reserve, one resident down layer is about `1.15 GiB`;
- all 48 down matrices in fp16 would be about `7.52 GiB` including that reserve, so this sizing point is borderline but fits the arithmetic budget on an 8 GiB card before other model state;
- at an effective `12 GB/s` H2D rate, gate/up residual plus base has a copy lower bound of `4.43 ms/layer`;
- if down is streamed as Q4 each token, total H2D becomes `88.70 MiB/layer` and the lower bound is `7.75 ms/layer`;
- if down receives the same 2-bit residual split, the ledger is `76.04 MiB/layer` and `6.64 ms/layer`.

Scaling the measured 2B full-chain compute proxy gives about `1.89 ms/layer` for the first sizing point. The copy term remains dominant, so an idealized FFN-only upper bound is about `4.70 tokens/s` for 48 layers with resident down, before attention, CPU routing, kernel launch gaps, fallback and other model weights. Streaming down reduces that bound to about `2.69 tokens/s`. For `hidden=6144, ffn=16384, layers=40`, the corresponding bounds are about `3.97 tokens/s` and `2.27 tokens/s`.

The current C++ CPU base evaluator is not proven to scale to this size. A simple linear extrapolation from the measured 2B gate+up base time (`1.96 ms` times the `5.625x` element ratio) is about `11 ms/layer`, which would exceed the `4.43 ms` H2D lower bound. The next runtime milestone therefore requires a stronger finite-formula evaluator, larger CPU parallel work units, or a policy that moves more structured base generation out of the critical path.

## GPU efficiency interpretation

From the measured 2B bridge (`tile=2048`):

- effective H2D: about `12.07 GB/s`;
- full-chain compute proxy: about `0.374 TFLOP/s`;
- proxy compute active time: `0.337 ms` of `0.948 ms` critical path;
- copy active time: `0.782 ms`;
- about half of the compute interval overlaps copy;
- residual/full-chain proxy density: about `10.67/13.34 FLOP per transferred byte` under the project’s accounting convention.

The measured proxy is only about `1.3%` of an estimated 28.6 TFLOP/s FP32 peak. That is expected for this batch-1 scalar-style prototype and is not a hardware occupancy guarantee. The useful result is that the GPU is no longer only doing a tiny residual kernel: SwiGLU and down extend the compute segment, while copy remains the limiting term.

## Decision

The architecture is **budget-feasible for a single FFN layer and for a 27B-class sizing model if down weights can remain resident or be handled by a second decomposed path**. It is **not yet guaranteed for an end-to-end 27B model on 8 GiB**. The unresolved hard limits are CPU base production at every layer, attention/other tensors, exact down decomposition, launch overhead at batch 1, and the actual layer count/dimensions of the target checkpoint.

The next required experiment is not another formula search. It is a multi-layer scheduler prototype that keeps the down policy explicit and measures CPU production, H2D, GPU compute and fallback on a continuous token stream.
