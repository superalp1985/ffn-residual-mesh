# 2026-09-03 Iteration 14

## 目标

把当前候选的近似包放入分页/超级块模型，检查连续 token 合并是否会吃掉带宽收益。

## 模型

- 近似包：`4112 B/token`（2048 维 fp16 基础输出 + top-k=4 系数/路由元数据）。
- fallback 权重代理：layer 23 down Q4 `10,321,920 B`。
- 超级块：64 KiB、256 KiB、1 MiB。
- 窗口：1、4、16、64、256、1024 token。

## 结果

仅近似包、无 fallback 时：

- batch=1：64 KiB/256 KiB/1 MiB 超级块分别造成 `65,536/262,144/1,048,576 B/token`，小包会被块粒度放大。
- 16 token 窗口：64 KiB 超级块约 `8,192 B/token`，256 KiB 约 `16,384 B/token`。
- 64 token 窗口：64 KiB 约 `5,120 B/token`，256 KiB 约 `8,192 B/token`。
- 256 token 窗口：64 KiB 约 `4,352 B/token`，256 KiB 约 `5,120 B/token`。

含 2% fallback 时，如果 fallback 权重在窗口内可复用：

- 64 token、256 KiB 超级块：约 `167,936 B/token`。
- 256 token、256 KiB 超级块：约 `45,056 B/token`。
- 1024 token、256 KiB 超级块：约 `14,336 B/token`。

若 fallback 页每 token 都被驱逐，流量会显著增加；因此页缓存和热度管理是实际收益的必要条件。

## 结论

1. 超级块不能固定为 256 KiB 或 1 MiB；decode 小 batch 需要较小粒度或等待窗口上限。
2. 64 KiB 更适合 16–64 token 的连续窗口；prefill 可用更大块，decode 应按延迟预算动态调整。
3. fallback 权重必须尽量在 GPU/显存中短时驻留并跨 token 复用，否则回退流量会吞噬近似收益。
4. 近似包与权重页应分开管理：前者顺序 ring buffer，后者热页缓存，不能用同一块大小。
