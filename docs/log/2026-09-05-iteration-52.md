# Iteration 52: first Qwen3.8-27B resident gate/up measurement

日期：2026-09-05

## 本轮完成

- 实现 `Qwen3.8-27B` 单层离线 artifact 编译器。
- 对 `Q4_K` gate/up 使用 32-code 分组的精确 `q=c+r` 拆分，残差固定为有符号
  4-bit，无裁剪。
- `down` 和非 `Q4_K` tensor 保留 exact fallback；当前模型是混合
  `UD-Q4_K_M`，不能把 IQ/Q3/Q5/Q6 当作 Q4_K 解码。
- 实现 Triton CUDA resident gate/up kernel，权重只在初始化上传一次。
- 实现计时器，分开记录动态 H2D、CPU base、GPU residual、CPU 提交 gap、
  merge/SwiGLU，以及串行原始 Q4 权重搬运对照。

## 第 3 层真实结果

输入是固定种子的合成 FP32 向量，**不是模型真实激活**。因此这不是端到端
生成速度或质量结论。

```text
gate/up exact decoded weight bit mismatches: 0
gate rel L2: 1.43e-7
up rel L2: 1.45e-7
SwiGLU rel L2: 2.13e-7
resident gate/up weight: 111,411,200 bytes
dynamic H2D per run: 159,744 bytes
residual weight H2D per run: 0
CPU base coefficient artifact: 44,564,480 bytes
```

热身后的 gate/up 最佳配置是 `block_rows=1, num_warps=4, CPU threads=8`：

```text
resident residual stream span: ~0.716 ms
CPU base: ~0.709 ms
wall path: ~1.032 ms
logical resident read / graph span: ~91.5 GB/s
registers/thread: 96
spills: 0
```

串行原始 Q4 gate/up 权重搬运对照：

```text
weight H2D: 100,270,080 bytes/run
weight H2D: ~7.96 ms
total gate/up stream: ~9.95 ms
```

接入第 3 层原始 `IQ4_NL` down 后，首版单块长归约约为 `15.7 ms`。按输入列
分块并做 partial reduction 后，完整单层关键路径降为：

```text
resident residual kernel: ~3.16 ms
SwiGLU + down: ~3.46 ms
critical path: ~6.83 ms
final output rel L2: 2.09e-7
```

这个优化仍直接读取原始 IQ4_NL 格式，不是把 down 解量化成 FP16 的替代路径。

驻留这一层时，运行时只发送激活和主项结果，确实避免了反复上传该层权重。
但这不是拆分独有的优势：原始 Q4 权重若能常驻，同样不需要重复上传。
本轮拆分后的 gate/up 驻留包反而比原始 Q4_K 大 11.1%，尚未解决全模型容量。
完整 FFN 单层已接入，attention、KV、窗口换入和生成循环仍未接入。

## 调优观察

- `block_rows=1` 最稳定；`block_rows=4` 已出现 register spill，`block_rows=8`
  出现严重 spill 和约 58ms 的异常退化。
- GPU 利用率不能用逻辑字节/时间替代；下一轮加入 Nsight/CUPTI 可用时再记录
  SM occupancy、DRAM throughput 和 kernel wait。
- 当前 CPU 主项仍是 dense coefficient dot：避免扫描逐权重主项，但每 token
  仍需读取约 42.5 MiB 的系数。不能把它描述成启动后 CPU 不读静态数据。
- IQ4_NL down 的输入分块显著降低了长归约的寄存器/调度压力；Q3/Q5/Q6/IQ4_XS
  后续也应分别实现格式专用分块核，不能强行共用 Q4_K kernel。
- 这里只记录了编译器资源统计；分块 down 后观察到的降时并不足以证明物理
  SM 利用率提升。CUDA event span 包含主机提交/WDDM 调度，graph 与普通
  event 计时仍有差异，没有以它们推断已“算满”。

## 容量与自适应计划

- 元数据扫描得到 5 个双 Q4_K gate/up 层：3、21、40、42、51。
- 64 个主层的原始 FFN 总计 9,861,980,160 bytes。
- 仅这 5 层采用 v1，其余保留原格式，FFN 账本为 9,917,685,760 bytes，
  约 9.24 GiB，仍超过 8 GiB，甚至还未加入 attention 等。
- `plan_resident_memory.py` 是容量规划器，不是已实现的异步调度器。
- 按本地 config，FP16 KV 在 batch=1、4K/8K/16K/32K context 下分别
  为 256/512/1024/2048 MiB。48 层线性注意力 FP32 递归状态估计 144 MiB，
  卷积历史另计约 5.625 MiB；具体后端状态类型还需核对。
- 采用假设的固定 1 GiB reserve 时，1/4/8 层双缓冲窗口容量可行。
  这没有证明 attention 权重/工作区都可放入 reserve，也没有证明传输能隐藏。
- 没有持久常驻层的纯滚动窗口，每次 decode sweep 仍需重新传约 9.92 GB
  权重；“窗口小”不等于“每 token 流量小”。因此目前不扩展运行全模型。

## 用户确认的下一阶段优先级

显存常驻残差为主，内存卸载为辅。下一版调度采用“持久常驻集合 + 小型预取
换入区”，不是每个 token 轮流搬所有层。主项留内存，只传输入相关结果；
已常驻残差不重复上传，缺失残差才从内存补入。回退原权重的流量必须单列。

最高目标是减少 GPU 等数据和主项结果的时间，提高有效计算效率与单 token
速度；不强求显存峰值下降，也不以增加无用计算换取表面上的 GPU 利用率。
预取是否真正隐藏等待、算子是否充分使用硬件，仍要通过实测确认。

本次只更新调度设计约束，没有新增性能测量；现有容量规划器和第 52 轮结果
不代表上述持久常驻调度已经实现。
