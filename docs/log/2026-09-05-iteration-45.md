# 2026-09-05 Iteration 45: Distributed Phone FFN Base Simulation

## Question

Can old phones act as a networked multi-CPU base-term pool, relieving the single CPU's cache and memory-bandwidth ceiling while the central GPU computes the exact residual path?

## Model

Added `scripts/simulate_phone_ffn_cluster.py`. This is an analytical scheduler simulation, not an Android benchmark. It models output-row sharding:

```text
phone workers hold disjoint compiled gate/up table rows
        -> receive a small quantized activation descriptor
        -> compute base rows in parallel
        -> return fp16 gate/up base rows
central GPU: residual H2D + residual reduction + base merge + SwiGLU + down
```

The per-layer critical path is modeled as:

```text
max(phone input + base compute + base return, GPU residual critical path)
```

The two branches can overlap after the layer activation is available.

## 27B-class default simulation

Assumptions:

- `hidden=5120`, `ffn=13824`, `layers=48`;
- block=4 radix table;
- 2048-row tile;
- phone memory bandwidth `18 GB/s`;
- network `1 Gb/s`, persistent-connection latency `0.35 ms`;
- phone L3 budget `8 MiB`.

Ledger:

- gate/up compiled table total: `8640 MiB` across the cluster;
- runtime table read: `33.75 MiB/token/layer` before row sharding;
- residual gate/up H2D: `50.625 MiB/layer` to the central GPU;
- activation descriptor to the phone pool: about `5.6 KiB/layer`;
- fp16 gate/up base returned from the pool: `54 KiB/layer`;
- central GPU residual critical lower bound at 12 GB/s PCIe: `4.42 ms/layer`.

At 1 Gb/s network and 2048-row tiles (corrected: `network_gbps` is gigabits/s; the earlier draft accidentally treated it as decimal GB/s):

| phones | table shard/phone | active tile table/phone | phone base ready | layer critical |
|---:|---:|---:|---:|---:|
| 1 | 8640 MiB | 1280 MiB | 3.15 ms | 4.42 ms |
| 2 | 4320 MiB | 640 MiB | 2.21 ms | 4.42 ms |
| 4 | 2160 MiB | 320 MiB | 1.72 ms | 4.42 ms |
| 8 | 1080 MiB | 160 MiB | 1.47 ms | 4.42 ms |
| 16 | 540 MiB | 80 MiB | 1.33 ms | 4.42 ms |
| 32 | 270 MiB | 40 MiB | 1.27 ms | 4.42 ms |
| 64 | 135 MiB | 20 MiB | 1.23 ms | 4.42 ms |

With the corrected network unit, phone base-ready times become approximately `3.15, 2.21, 1.72, 1.47, 1.33, 1.27, 1.23 ms` for `1, 2, 4, 8, 16, 32, 64` phones. The GPU residual path remains `4.42 ms/layer` at the assumed 12 GB/s PCIe rate, so the cluster still removes the CPU branch from the critical path but does not by itself raise the theoretical layer rate.

At a 24 GB/s PCIe-equivalent residual path (`2.21 ms/layer`), two phones are enough to approach the GPU branch under the 1 Gb/s network assumption; at 2.5 Gb/s, two phones are below that GPU bound. More phones then provide redundancy, thermal/failure tolerance and batch throughput rather than single-token latency reduction.

The GPU residual transfer is still dominant in this configuration. The phone pool does not increase the idealized decode rate after about two workers, but it creates substantial headroom for CPU base production and makes the CPU side no longer the critical path.

## L3-oriented tile simulation

With `tile_rows=512`, `network=2.5 Gb/s` and the same 8 MiB phone L3 budget:

- total active tile table is `320 MiB` before sharding;
- 32 phones reduce it to `10 MiB/phone`;
- 64 phones reduce it to `5 MiB/phone`, which fits the modeled L3;
- the simulation then applies a 2x local cache-bandwidth multiplier;
- phone base ready time reaches a network floor around `0.74 ms/layer`.

This supports the user's intuition: the cluster is not merely “more CPU cores”. It is a distributed cache hierarchy in which table shards and active tiles can be placed close to different CPU caches.

## Constraints

The simulation does not prove real performance. The main unresolved costs are:

- Wi-Fi variability and per-message latency;
- Android scheduling, thermal throttling and background suspension;
- batch=1 autoregressive layer dependency;
- aggregation and ordering of row-sharded base outputs;
- phone failure and re-routing;
- down projection policy, which remains central to total PCIe traffic.

The practical transport should use persistent streams, binary packets, tile sequence numbers, deadlines and a GPU fallback path. A phone should not be contacted through a fresh RPC for every tile.

The control descriptor is only about `5.6 KiB/layer`; fp16 gate/up base return is about `54 KiB/layer` in total. Input broadcast can be multicast or replicated from one send buffer. Base return traffic is not multiplied by phone count when row-sharding, but the center's aggregate uplink must still carry the complete `54 KiB/layer`; simultaneous phone replies only reduce latency if the network fabric has matching aggregate capacity.

## Decision

The idea is **architecturally meaningful**. A phone pool can turn the single-CPU L3/RAM wall into an aggregate distributed-memory and distributed-bandwidth resource. The current simulation says the first benefit is not higher tokens/s by itself; it is keeping the CPU base branch safely ahead of GPU residual work. Once the GPU residual path is optimized or the residual payload is reduced, the phone count can become a real throughput lever.

The next experiment should be a two-process loopback prototype on one PC: emulate several phone workers with pinned worker processes, persistent sockets and row-sharded table files, then measure actual fan-out, return aggregation and deadline misses before using real Android devices.
