# 2026-09-04 Iteration 34: GPU Wait Is the Primary Target

## User correction

VRAM peak does not have to decrease. A larger resident working set is acceptable when it prevents the GPU from waiting for weight transfers, provided the process remains below the device capacity.

## Revised objective order

```text
1. reduce GPU copy/sync waiting
2. increase H2D and kernel overlap
3. increase sustained GPU operator utilization
4. reduce H2D bytes/token where it helps the pipeline
5. keep VRAM peak below OOM; no relative reduction requirement
```

This changes the systems experiment. Larger residual windows and double/triple buffering are valid even when they do not reduce resident bytes. The relevant comparison is not static residency alone, but whether the GPU has a ready residual tile whenever the kernel reaches its next launch.

## Consequences for the algorithm

- Keep the residual exact; do not introduce lossy clipping just to minimize VRAM.
- Permit several residual superblocks resident at once.
- Use cold-start expansion to build a prefetch schedule and page reuse order.
- Measure copy-engine wait, kernel wait, overlap ratio, sustained SM/operator utilization, H2D bytes/token, and VRAM peak together.
- Reject only OOM or a path whose additional CPU/base-output synchronization outweighs the GPU wait reduction.

The main-term requirement remains unchanged: runtime must not scan raw weights or an equivalent dense expanded main-term stream. It must use compiled formulas/partial sums while the exact residual pipeline keeps the GPU fed.
