# ffn-residual-mesh

GitHub Release title: `ffn-residual-mesh`  
Suggested tag for this revision: `v0.1.0-rc3`

这是 `ffn-residual-mesh` 的第一个公开 release candidate。

它研究的不是“再做一个模型分片器”，而是一个更具体的硬件资源交换问题：**GPU 有计算能力，却经常等不到数据；主机内存、平板和旧手机有大量存储和串行计算能力，却无法直接参与 GPU 的高密度算子。**

本项目的做法是：

> **冷启动时把 FFN 权重预展开、分区和编译；运行时把臃肿的 base 留在主机/平板内存，只把紧凑 residual 搬到中心 GPU，再在非线性之前精确合并。**

简单说，就是用更多 GPU 算力和冷启动时间，换显存容量与内存/显存之间的带宽压力。

## 这次 Release 的核心

- 分层 FFN 拆分/合并算法
- 量化整数域中的精确重建路径
- CPU/主机 base + GPU residual 的 CUDA 桥接实验
- MiniMax H3 + ComfyUI 手机/平板集群模拟
- TeaCache real/reuse step 账本
- 手机/平板 worker 的 loopback 协议原型
- Qwen3.8-27B-class 的显存和带宽预算

重点不是减少 FLOPs。重点是让每一个传到 GPU 的字节触发更多连续计算，让 GPU 少等数据。

## 算法怎么来的

标准 gated FFN 可以写成：

```text
g = W_gate x
u = W_up   x
h = SiLU(g) * u
y = W_down h
```

我们把每层权重拆成两部分：

```text
W = B + R
```

其中：

- `B` 是冷启动时预展开的 base，适合放在主机 RAM 或平板内存；
- `R` 是不规则 residual，集中交给 GPU 做高密度计算。

于是：

```text
g = Eval(B_gate, x) + Eval(R_gate, x)
u = Eval(B_up,   x) + Eval(R_up,   x)
h = SiLU(g) * u
y = W_down h
```

注意，gate 和 up 必须在进入 SiLU 之前合并。不能先分别激活再相加，否则一般不等价。

## 为什么拆分可以保持精度

最直观的例子是：

```text
(a + b) * (c + d)
= ac + ad + bc + bd
```

这里 `a`、`c` 可以代表规律性强、适合预展开的主项，`b`、`d` 代表需要精确处理的细节。真正的实现不能把交叉项偷偷丢掉；它们要么进入 base 公式，要么进入 residual 计算。

在量化整数域里，同样的规则成立。以一组量化权重为例：

```text
q[i] = C[index[i]] + r[i]
```

点积可以写成：

```text
sum(x[i] * q[i])
= sum(C[index[i]] * x[i])
  + sum(x[i] * r[i])
```

第一项是有限状态的基项聚合，第二项是完整 residual。只要 residual 不被裁剪，合并结果就能在选定的整数/量化域内严格重建原始点积。允许误差的路径另行测量，并且保留中心 GPU 精确 fallback。

这也是本项目和普通“近似压缩”的区别：**核心 exact 路径不是把重要数字删掉，而是改变它们的存放位置和计算时机。**

## 运行时数据流

```text
冷启动：原始量化权重
    -> 完整扫描一次
    -> 编译 base 公式、部分和、residual tile、scale、索引
    -> 主机 RAM / 平板 worker 常驻

运行时：输入 tile
    -> CPU/worker 生成 base
    -> GPU 接收 residual tile
    -> 合并 gate/up
    -> 原始 SwiGLU
    -> down、attention、decode
```

正常运行不能再次顺序扫描等价的稠密主项权重流。否则只是换了一个名字，带宽问题并没有解决。

## 手机和平板集群的应用前景

第一阶段不追求让手机代替 GPU，而是让它们成为 FFN base worker：

- 主机 RTX 4070 保留 GPU residual、SwiGLU、down 和 Attention；
- 平板或旧手机保存编译后的 FFN base 分片；
- 中心端广播输入 descriptor；
- worker 并发返回 base tile；
- 任意 worker 超时或校验失败，立即回退中心 GPU 精确路径。

最适合的硬件顺序是：

1. 同机 loopback 多进程
2. USB/USB-Ethernet 平板
3. 10GbE 平板小集群
4. 有线手机集群
5. 普通 Wi-Fi 手机集群

对 MiniMax H3 的模拟表明，精确 gate/up 回传在 1 Gb/s 下约为 839.8 MiB/real step，网络会成为关键路径；在 10 Gb/s 下，worker 分支可以隐藏在 GPU 分支之后。这个结果支持先做有线平板，而不是先堆几十台 Wi-Fi 手机。

## ComfyUI 方向

目标不是把 ComfyUI 工作流拆成很多 RPC 节点，而是提供一个可选的模型 backend：

```text
ComfyUI
  -> TeaCache 判断 real/reuse step
  -> FFN worker backend
  -> GPU residual + merge
  -> 原有 SwiGLU/down/SageAttention 路径
```

TeaCache 的 reuse step 不需要重新调用手机 worker，因此可以直接减少集群流量。MiniMax H3 是当前最合适的验证对象，后续可以扩展到更大的 dense 模型和 27B-class 语言模型。

## 还没有宣称什么

- 没有宣称 27B 已经在 8 GiB 显卡上端到端跑通；
- 没有宣称手机数量越多就一定越快；
- 没有把 hidden 近似路径当成 exact；
- 没有把模拟结果当成 Android 实测；
- 没有替代 TeaCache、SageAttention 或 ComfyUI 的精确 fallback。
